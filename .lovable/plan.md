# تطوير مشروع الأوردرات والمخازن + الانتقال إلى قاعدة بيانات Lovable

الهدف: الحفاظ على المشروع الحالي كما هو (صفحات HTML وCSS وJS بنفس التصميم والألوان والخطوط وأسماء الصفحات)، مع نقل البيانات من Firebase إلى قاعدة بيانات Lovable Cloud بشكل تدريجي وآمن.

## المرحلة 1 — إدخال المشروع الحالي كما هو

- نسخ كل ملفات المشروع (بدون ملفات النسخ الاحتياطي والمكررة) إلى مجلد الملفات الثابتة، فتُفتح الصفحات بنفس روابطها الحالية: `/index.html`، `/main.html`، `/all-orders.html`، `/مخازن/index.html`، `/moled/index.html` … إلخ.
- الصفحة الرئيسية للموقع تفتح على صفحة تسجيل الدخول الحالية كما هي الآن.
- لا تعديل على التصميم أو النصوص في هذه المرحلة، فقط التأكد من أن كل صفحة تفتح وتعمل كما كانت.
- استثناء الملفات غير المستخدمة من النسخ: `all-orders.html.backup_*`, `temp_check.html`, `public_check/`, `ledoux-local/`, ملفات PHP وملفات JS الفارغة، وسكربتات `tools/` — تبقى محفوظة لكن خارج الموقع.

## المرحلة 2 — تشغيل قاعدة بيانات Lovable وبناء الجداول

تشغيل Lovable Cloud (قاعدة بيانات + مستخدمين + ملفات + دوال خدمة) وبناء جداول مقابلة لمجموعات Firestore الحالية:

- الأوردرات: `orders`, `orders_best_sweet`, `drafts`, `send_orders`
- الكتالوج والمخازن: `catalog`, `products`, `materials`, `sections`, `suppliers`, `warehouses`, `transfers`, `inbound`, `outbound`, `purchase_requests`, `requisitions`, `inventory_audit`
- المولد: `moled_items`, `moled_invoices`
- بقية النظام: `users`, `invoices`, `reservations`, `chat_messages`, `chat_users`, `settings`, `counters`, `urgent_news`, `suggestions`, `activity_logs`, `reports`
- كل جدول يحتوي الأعمدة الأساسية (رقم، تاريخ، فرع، حالة، مستخدم…) مع عمود مرن يحفظ بقية الحقول كما هي، حتى لا تُفقد أي بيانات ذات شكل غير ثابت.

## المرحلة 3 — طبقة وصول واحدة للبيانات (أهم خطوة)

الكود الحالي يتعامل مع البيانات عبر واجهة موحّدة تقريبًا (`window.firebaseHelpers` ونداءات `collection(...)`). سيتم:

- إنشاء ملف واحد `data-layer.js` يوفّر نفس الأسماء والدوال الحالية (إضافة، تحديث، حذف، قراءة الكل، متابعة التغييرات) لكن مصدر البيانات هو Lovable.
- استبدال سطر تحميل Firebase في الصفحات بسطر تحميل هذا الملف — تعديل سطرين أو ثلاثة في كل صفحة فقط، بدون لمس التصميم أو منطق الصفحة.
- التحويل يتم صفحة بصفحة (نبدأ بصفحة واحدة للتجربة والاتفاق على النتيجة، ثم الباقي بالترتيب الذي تحدده).

## المرحلة 4 — نقل البيانات الموجودة

لنقل بياناتك الحالية أحتاج منك أحد الأمرين:

1. تصدير البيانات من Firebase (ملف JSON لكل مجموعة) وإرساله لي، أو
2. مفتاح خدمة (Service Account) لمشروع Firebase لأقوم بالتصدير والنقل بنفسي.

بعدها أنقل السجلات مع الحفاظ على الأرقام والتواريخ والمعرفات المرتبطة، وأقارن عدد السجلات قبل وبعد للتأكد.

## المرحلة 5 — تسجيل الدخول والصلاحيات

الوضع الحالي: كلمة المرور محفوظة كنص، والصلاحيات تمر في الرابط وتُخزَّن في المتصفح، فيمكن لأي شخص تعديلها أو فتح الصفحات مباشرة.

الخطة: الإبقاء على شكل صفحة الدخول كما هو تمامًا، مع تسجيل دخول حقيقي في الخلفية، وجدول صلاحيات منفصل، وحماية على مستوى قاعدة البيانات بحيث لا يرى المستخدم إلا ما يُسمح له به. تُنفَّذ بعد استقرار المراحل السابقة.

## المرحلة 6 — تحسينات تدريجية (بدون تغيير الشكل)

- توحيد إعداد الاتصال في ملف واحد بدل نسخ متعددة.
- توليد صفحات الفروع المتشابهة من إعداد واحد بدل تكرار نفس الكود في كل صفحة.
- تحميل السجلات بفلترة وترقيم صفحات من قاعدة البيانات بدل تحميل كل السجلات ثم الفلترة في المتصفح.
- استبدال دالة المساعد الذكي الحالية بخدمة الذكاء الاصطناعي في Lovable.

## تفاصيل تقنية

- المشروع يُخدَّم كملفات ثابتة من `public/` داخل قالب TanStack Start الحالي، فلا يتغير أي هيكل داخل صفحاتك.
- `data-layer.js` يستدعي Lovable Cloud عبر مفتاح النشر العام مع سياسات RLS، وواجهته متوافقة مع `window.firebaseHelpers` الحالية لتقليل التعديلات.
- المتابعة الحية للتغييرات (`onSnapshot`) تُقابل بـ Realtime channels على الجداول التي تحتاجها فعلًا (الشات، الأوردرات، الأخبار العاجلة).
- بادئة `stock_` في مجموعات المخازن تصبح مجرد أسماء جداول واضحة، مع خريطة أسماء داخل طبقة البيانات حتى لا تتأثر الصفحات.
- ملفات الاستضافة القديمة (`firebase.json`, `.htaccess`, `functions/`) تبقى في المستودع للمرجعية دون تفعيل.

## نقاط تحتاج قرارك

- أي صفحة نبدأ بها التحويل التجريبي (مقترحي: `all-orders.html`).
- طريقة تصدير بيانات Firebase (ملفات JSON أم مفتاح خدمة).
